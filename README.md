# edge-vibe-sentinel

**A condition-monitoring prototype for motors and actuators, with vibration features, operating-context baselines, latched alerts and an offline queue.**

Version **0.1.0** runs entirely on a computer with Python 3.11 or newer. It requires no controller, accelerometer, network service or third-party Python packages. The included measurements are explicitly **simulated**. This is an independent maintenance project.

## Try the project

Open a terminal in this repository:

```powershell
python -m edge_vibe demo --output demo-output
```

Open `demo-output/report.html` in a browser. The repository's `examples/demo/` keeps the small demo artifacts (baseline, config, summary, events, queue batches, CSV); the large waveform files and the report (several megabytes) and the SQLite outbox are not committed and are regenerated by the command above in a few seconds. The report works offline and contains selectable X/Y/Z waveforms, normalized FFT spectra, acceleration trends, thresholds, an assessment log, alert evidence and queue statistics. It can download the selected raw window as JSON.

The demo contains 15 reference windows and 28 monitoring windows. It produces two raised alarms and two recoveries, finishing with no latched alarm. Its cases include startup, changed motor speed, actuator extend/retract phases, missing samples, clipping, a sensor remount and housing-temperature excursions. An insufficient baseline or invalid window is shown explicitly.

On a **fresh output directory**, the SQLite demo queues 32 summaries/events, rejects duplicate insertions, performs a clearly simulated acknowledgment of 10 records, and leaves 22 pending. No server is contacted. The database persists between runs; use a new output directory when repeating the demo for these exact queue counts.

## What is implemented

- Three-axis demeaned acceleration RMS, peak, crest factor, vector RMS, Hann-windowed FFT amplitude and band RMS.
- Frozen baselines fitted only from explicitly approved reference windows with valid acquisition quality.
- Separate groups for device, asset, provenance, mounting, sensor configuration, sample rate/count, motor speed/load bins and actuator phase.
- Repeated-window alarm entry, lower recovery thresholds, timestamp-gap checks and alarm retention through unavailable or invalid measurements.
- JSONL input/output, CSV export, a self-contained HTML report and a persistent SQLite store-and-forward outbox.
- Numerical and workflow tests (67), MIT license, packaging metadata and a GitHub Actions workflow. See [CHANGELOG.md](CHANGELOG.md).

This version reports acceleration in **g**. It does not diagnose a bearing fault, estimate remaining useful life, calculate vibration velocity severity or claim compliance with a condition-monitoring standard. It contains no live acquisition, ESP32 firmware, cloud endpoint or automatic upload. A housing temperature is not a winding temperature.

## Import and analyze windows

Use the [data contract](docs/data-format.md) to export records from a future acquisition adapter. The following commands use the simulation data produced by `python -m edge_vibe demo --output examples/demo` (run it first if `examples/demo/windows.jsonl` is absent):

```powershell
python -m edge_vibe train examples/demo/references.jsonl --config examples/demo/config.json --output work-output/baseline.json
python -m edge_vibe features examples/demo/windows.jsonl --output work-output/features.jsonl
python -m edge_vibe analyze examples/demo/windows.jsonl --baseline work-output/baseline.json --output work-output/analysis
python -m edge_vibe report examples/demo/windows.jsonl --baseline work-output/baseline.json --output work-output/report.html
```

`analyze` writes raw windows, a copy of the baseline, assessments, events, measurements CSV, summary JSON and the HTML report. Records must be strictly chronological within each device/asset stream; duplicate identities are rejected. The report is regenerated from raw data and the model.

Exit code **0** means the command completed and, for `analyze`, no stream has a final latched alarm. It does **not** mean every window was assessable or an asset is healthy: inspect the assessment counts. `summary.json` also lists `final_alarm_by_stream`, the latched state of every device/asset stream, so one alarmed asset is not hidden by the aggregate flag. Code **1** means analysis completed with a final active alarm. Code **2** indicates invalid input or an operational error. `report` returns 0 when it creates its file, regardless of alarm state.

## Offline outbox

```powershell
python -m edge_vibe outbox enqueue examples/demo/assessments.jsonl --db work-output/outbox.sqlite
python -m edge_vibe outbox enqueue examples/demo/events.jsonl --db work-output/outbox.sqlite
python -m edge_vibe outbox export --db work-output/outbox.sqlite --output work-output/batch.json --limit 100
python -m edge_vibe outbox status --db work-output/outbox.sqlite
```

Exporting does not acknowledge messages. A future delivery adapter should send the batch and confirm acceptance before calling:

```powershell
python -m edge_vibe outbox ack work-output/batch.json --db work-output/outbox.sqlite
```

Only acknowledge messages whose delivery has actually been confirmed. Acknowledgments verify the IDs and content hashes against queued messages. Conflicting content under the same ID is rejected, and failed multi-message operations roll back. Queue persistence and deduplication are local properties; no end-to-end delivery guarantee exists. Raw waveforms and FFT arrays stay in the analysis files; the queue holds compact scalar summaries and alert evidence references.

Acknowledged messages stay in the database until pruned, which bounds local storage on a long-running node:

```powershell
python -m edge_vibe outbox prune --db work-output/outbox.sqlite --keep 100
```

Pruning never removes pending messages. Because deduplication is keyed on queued records, a pruned record ID could be enqueued again; a receiver must keep its own duplicate handling, as the roadmap already requires.

## How decisions work

A reference label is an operator's external judgment that an asset is suitable for baseline collection. Software never decides that a window is a healthy reference and never updates the model while monitoring. Defaults use at least five approved windows per context, a median/MAD-derived RMS threshold, three consecutive breaches to raise an alarm and two consecutive recovered windows to clear it. These are demonstration settings, not validated industrial limits.

Alarm entry uses **full-window demeaned vector acceleration RMS**, or excessive housing temperature, in an eligible context with a ready baseline. Band RMS is an inspection feature and does not drive the alarm. Recovery requires both quantities to be below their clear limits. Invalid, transitional, missing-context and unknown-baseline windows interrupt pending streaks and preserve existing alarms. Returning to the alarm's original context is necessary for its automatic recovery. A normal window in another context can coexist with a latched alarm.

## Development and GitHub

```powershell
python -m unittest discover -s tests -v
python -m compileall -q edge_vibe tests
```

With Node.js available, the optional report smoke test checks JavaScript syntax, embedded demo data, selection, filtering and export handler execution using a small DOM substitute:

```powershell
node tests/report-smoke.cjs examples/demo/report.html
```

This is not a browser layout or rendering test.

Optional installation, including the `edge-vibe` console command:

```powershell
python -m pip install .
edge-vibe --help
```
